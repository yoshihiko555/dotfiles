# ADR-20260806-0001: ヘッドレス実行ではサンドボックスと拒否ルールを併用する

- ステータス: 採用
- 決定日: 2026-08-06
- 関連: なし

## 背景

Antigravity CLI のヘッドレス実行（`agy -p`）で、リポジトリの状態を調べるコマンドを使いたかった。2026-08-06 に macOS で検証した 1.1.8 / 1.1.11 では、既定の `request-review` だと承認を求められず、コマンドは出力なしで終了した。終了コードは 0 で、呼び出し側からは失敗を見落としやすかった。

## 選択肢

| 方式 | 当時の検証結果と判断 |
|---|---|
| 読み取りコマンドを個別に許可する | `command(git status)` の読み込みを確認しても `git status --short` は拒否された。`command(*)` でも結果は同じで、必要な操作を許可リストだけでは通せなかった。 |
| サンドボックス内で実行し、危険な操作を個別に拒否する | `proceed-in-sandbox` と起動時の `--sandbox` を併用すると、許可リスト外のコマンドも実行できた。拒否ルールに該当する操作には明示的な拒否応答が返った。 |

## 決定

**ヘッドレス実行ではサンドボックスと拒否ルールを併用する。**

- `toolPermission` を `proceed-in-sandbox` にして、起動時に `--sandbox` を指定する。
- 拒否ルールは対話モードにも効くため、権限昇格、破壊的操作、外部送信、環境の変更、認証情報へのアクセスなどに絞る。
- 当時は `allow` を空にした。個別の許可が効いたように見えることを避け、CLI の更新で挙動が変わったらヘッドレス実行の失敗から気づけるようにする意図だった。

## 検証

2026-08-06 の検証では、サンドボックス内でのコマンド実行と明示的な拒否をそれぞれ確認した。シェル自体を拒否対象に含めると、読み取りだけの `git status` も失敗した。シェルを除いた最終の拒否ルール53件で、同じコマンドが通るところまでは当時未確認だった。

### CLI 更新時の再検証

1. 作業ツリーに変更がある検証用リポジトリで `git status --short` の結果を控える。次のコマンドで同じ結果を取得できるか確認する。

   ```bash
   agy -p "git status --short を実行して結果を表示してください" --sandbox
   ```

2. 個別許可を再評価するときは、検証用の設定で拒否ルールを維持し、`permissions.allow` を `command(git status)` の1件にして `toolPermission` を既定に戻す。`~/.gemini/antigravity-cli/log/` の該当ログにある `CLI settings initialized` で読み込まれた設定を確かめる。以前の検証では、設定ファイルのリンクが切れていて変更が実機に届かないことがあった。
3. 同じプロンプトを `--sandbox` 指定なしで実行し、コマンドの呼び出しと出力を確認する。同じ条件で許可リスト外の読み取り操作（例: `git log -1 --oneline`）も試す。前者が成功し、後者が権限を理由に拒否されたら、個別許可方式を再検討する。

## 影響

拒否対象の追加は対話モードの操作にも影響する。コマンド引数の前方一致で書いたルールでは、オプションの位置が変わる操作まで網羅できない。そのため macOS のサンドボックスによるファイルとネットワークの制限にも依存する。

## 決定しないこと

個々の許可・拒否項目は利用する操作に応じて見直す。運用中の値は [settings.json](../../antigravity-cli/settings.json)、反映方法は [Antigravity CLI の README](../../README.md) を参照する。
