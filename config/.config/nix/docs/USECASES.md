# Nix ユースケースカタログ（次に何をやるかの判断材料）

「Nix を使うと何ができるか」を価値・コスト・向き不向きの軸で並べたカタログ。
**進行状態・着手順の正典は [ROADMAP.md](ROADMAP.md)**（本書は状態を持たない）。
各項目の () 内は ROADMAP の対応番号。

---

## すでに手に入れた能力（2026-08-01 時点）

振り返り用。「Nix 化して何が変わったか」の実績。

| 能力 | 具体的に何が起きたか |
|---|---|
| 宣言的パッケージ管理 + zap | 宣言外の brew が自動削除される。「いつの間にか入っていた/消えていた」が構造的に消滅 |
| dotfiles 配線（mkOutOfStoreSymlink） | stow と同じ編集即反映のまま、ホスト差分（hermes の tmux 等）も宣言で表現 |
| launchd 宣言管理 | llama-swap / miniserve が手書き plist から宣言生成に。マシン再構築時も switch 一発 |
| 世代管理 / rollback | switch のたびにスナップショット。数秒で切り戻し可能 |
| multi-host | 1 つの flake で hermes を管理。MBP / WSL2 も同じ骨格に載る |
| 環境の自己文書化 | 「マシンに何が入っているか」= リポジトリのファイル。git 履歴が変更ログ |

## 候補カタログ

### 実利が大きいもの

| 項目 | 何が嬉しいか | コスト | 向き不向き・備考 |
|---|---|---|---|
| **Remote builders**（4-1） | MBP の `darwin-rebuild` の重いビルドを hermes に委譲。メイン機のファン爆音・CPU 占有から解放 | 中（SSH 経由の builder 登録 + 信頼設定） | **stow では原理的に不可能な唯一の価値**。両機 aarch64-darwin なので成果物がそのまま使える。前提の Phase 3-1 はクリア済み |
| **flake check + CI**（4-3） | push 時に設定の破綻を自動検出。壊れた宣言が main に入らなくなる | 小〜中（GitHub Actions 追加。リポジトリに CI が無いので純増） | `link-tmux` の腐敗はこれがあれば検出できていた。**Phase 3-2（メイン機）の前に入れると保険になる** |
| **セキュリティ / OS 設定の宣言管理**（4-8・新設） | ゲストログイン無効・画面ロング・Touch ID sudo 等を宣言化。新端末でのセキュリティ設定漏れが構造的に消える | 小（system.defaults / security.pam の宣言追加のみ） | hermes で安全に検証可能。**ファイアウォールだけは要設計**（miniserve の 0.0.0.0 公開と干渉） |
| **comma + nix-index**（4-2） | `, jq` のように未インストールのコマンドをその場で実行。「一回だけ使いたい」のためにインストールしなくてよい | 極小 | 導入コストほぼゼロの quick win |

### 運用を楽にするもの

| 項目 | 何が嬉しいか | コスト | 向き不向き・備考 |
|---|---|---|---|
| **Cachix Deploy**（4-4） | hermes が push 型でなく pull 型で設定に自動追従。「SSH して pull + switch」が不要に | 中（外部サービス依存が増える） | まず手動運用に慣れてから。現状の運用頻度なら急がない |
| **sops-nix**（4-5） | 秘匿情報を暗号化したままリポジトリにコミット。マシンごとの手動配置が不要に | 中（鍵管理の設計が必要） | トリガー: 3 台目が実稼働し手動配置が負担になったとき |
| **nh**（4-7） | rebuild の UX 改善・差分表示（何が変わるか事前に見える） | 極小 | switch 前に差分確認できると安心感が上がる |
| **specialisation**（4-6） | 同一ホストの設定バリアント切替（ccw/taktw の会社アカウント切替の宣言化） | 中 | 現状 zsh 関数で動いているため急がない。home-manager 版は実験的機能 |

### 表現力を広げるもの（Tier 2）

| 項目 | 何が嬉しいか | コスト | 向き不向き・備考 |
|---|---|---|---|
| **自作パッケージ**（4-7） | nixpkgs 未収録の CLI（git-gtr / agent-browser / takt）を宣言に載せる。**git-gtr を自作化すると brew の git 依存も消える** | 中（derivation の学習） | git-gtr は純シェル実装なので初めての題材に最適 |
| **overlays**（4-7） | nixpkgs のパッケージを部分上書き・patch。upstream が壊れても自分で直せる | 中 | 必要になった時に。乱用すると更新追従が重くなる |
| **dockerTools**（4-7） | Dockerfile なしで OCI イメージ生成。レイヤ最適化が自動 | 中 | コンテナを日常的にビルドする用途が出てから |
| **flake templates**（4-7） | `nix flake init -t` でプロジェクト雛形 | 小 | プロジェクト立ち上げ頻度次第 |

## 判断の軸（迷ったときのガイド）

1. **実利が先、学習は従**: ADR-0003 の「正直な前提」の通り、Nix は学習込みの投資。
   ただし次の一手を選ぶときは実利（時間・安全性が具体的に改善するか）を優先する
2. **メイン機に触る前に保険を**: Phase 3-2（MBP）の前に CI（4-3）を入れる価値は高い
3. **外部依存は最後**: Cachix / sops など外部サービス・鍵管理が絡むものは、
   手動運用の痛みを実感してから
4. **1 switch = 1 変更クラス**: 検証はカテゴリを混ぜず、小さく切って rollback 可能に保つ
