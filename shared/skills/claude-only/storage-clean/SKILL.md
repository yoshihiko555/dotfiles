# storage-clean

## このスキルの立ち位置

Mac のストレージ整理には2種類の作業が混ざっている。

1. **システムキャッシュ・アプリ残骸の掃除** → BuhoCleaner（GUIアプリ）の仕事。このスキルはここに手を出さない。
2. **開発ツールのキャッシュ・成果物の掃除** → uv / npm / pnpm / go / Homebrew / pre-commit のキャッシュ、OrbStack のイメージ、ghq 配下の古い `node_modules` / `.venv`、takt の完了済みワークツリー。これがこのスキルの守備範囲。

このスキルは対話的に実行するものであり、無人の定期実行は行わない（削除を伴う作業を自動化するとリスクが高いため、まずは実行するたびに人が確認する形で精度を上げる）。

Nix store の世代管理は `nix.gc.automatic` の宣言的な週次GCに任せてあるので、このスキルはその設定が生きているかを確認するだけで、GC自体には手を出さない。

## 全体フロー

1. 前回実行ログとの差分表示 + 現状測定
2. BuhoCleaner を起動してもらう案内 → 完了後に再測定
3. safe カテゴリの即時 prune（承認不要）
4. gray カテゴリの提示 → `AskUserQuestion` で1カテゴリずつ承認を取ってから削除
5. スコープ外の大物をレポートするだけ（削除しない）
6. 最終測定 → ログに1行追記

途中で気が変わったら、そこで打ち切ってよい。最終測定とログ追記はできる範囲でスキップしても構わない（無理に完走させる必要はない）。

## ステップ1: 現状測定

`scripts/measure.sh` を実行する。ディスク空き容量と、このスキルが扱う全カテゴリのサイズを一覧表示する読み取り専用スクリプトなので、まずこれを叩けば全体像がつかめる。

```
bash <skill-dir>/scripts/measure.sh
```

`~/.local/state/storage-clean/history.log` を確認し、前回の記録があれば「前回の空き容量 → 今回の空き容量」の差分を一言添える。ログの形式は以下（タブ区切り、1行1回分）。

```
2026-08-14	空き109G	空き118G	memo
```

ファイルが無ければ気にせず先に進む（初回実行として扱う）。

## ステップ2: BuhoCleaner の案内

システムキャッシュ・アプリケーションサポートの掃除は BuhoCleaner の担当。ここでは「BuhoCleaner を起動してひと通りクリーンアップしてください」と案内し、ユーザーが完了したと言ったら `df -h /System/Volumes/Data` で空き容量だけ再確認する。BuhoCleaner の操作自体を代行しようとしない（GUIアプリなので手が出せないし、対象外と決めた領域でもある）。

## ステップ3: safe カテゴリ（承認なしで実行してよい）

以下はいずれも公式のキャッシュ管理コマンドで、消えても再生成される。存在しない・コマンドが入っていないものは黙ってスキップしてよい（`command -v` で確認してから叩く）。

| コマンド | 対象 |
|---|---|
| `uv cache prune` | uv の未参照パッケージのみ（全消しの `uv cache clean` は gray） |
| `npm cache clean --force` | npm キャッシュ |
| `pnpm store prune` | pnpm の未参照パッケージのみ |
| `go clean -cache` | go のビルドキャッシュ（`-modcache` は含めない、再取得コストが高いため gray） |
| `brew cleanup --prune=all` | Homebrew の古いバージョン・ダウンロードキャッシュ |
| `pre-commit gc` | pre-commit の未使用フック環境 |

実行後は各コマンドの標準出力をそのまま見せる（何をどれだけ消したかがそこに出る）。失敗したものがあっても他のコマンドは続行する。

注意: `uv cache prune` は uvx 常駐プロセス（chroma-mcp や cocoindex などの MCP サーバー）が `~/.cache/uv/.lock` を握っているとロック待ちタイムアウトで失敗する。uvx の一時環境はキャッシュ内に置かれるため、`--force` での強行は稼働中プロセスを壊すリスクがあり不可。`pgrep -fl uvx` で常駐が確認できたらこの項はスキップし、その旨を報告する（uv は 16GB 級で一番大きい項目なので、いつか回収したければ MCP サーバー停止中に手動実行する選択肢を添える）。

## ステップ4: gray カテゴリ（毎回承認を取る）

`measure.sh` の出力にある gray セクションのサイズを見せながら、`AskUserQuestion` でカテゴリごとに「今回やる/やらない」を確認する。まとめて一括承認ではなく、カテゴリごとに独立した判断にする（性質がそれぞれ違うため）。

### OrbStack
`docker system df` でイメージ・コンテナ・ボリュームの内訳を見せ、`docker system prune` に何を含めるか（未使用イメージだけか、停止中コンテナも含むか）をすり合わせてから実行する。稼働中のコンテナに影響する操作なので、いきなり `-a` や `--volumes` を付けない。

### takt の `.worktrees`
`measure.sh` が列挙した `.worktrees` 配下のクローンについて、各クローンのブランチが `main`/`master` にマージ済みかどうかを確認してから提示する。このリポジトリ群は squash merge 運用のため、`git log <base>..HEAD` のコミット有無だけでは「マージ済みなのに未マージ」に見える誤判定が起きる。`git -C <clone> diff <base>...HEAD` の内容差分が空かどうかで裏取りし、未コミット変更（`git status`）が無いことも確認する。未マージの変更が残っているクローンは候補から外し、その旨を伝える。承認が取れたものだけ `rm -rf` する。

### ghq の古い node_modules / .venv
`measure.sh` が「90日以上コミットのないリポジトリ」として列挙したものだけを候補にする（アクティブなリポジトリは対象にしない、というのがこのスキルの判断基準）。リポジトリ名とサイズ、最終コミットからの経過日数を見せて、削除するものを選んでもらう。`node_modules` は `npm install` / `pnpm install`、`.venv` は `uv sync` 等で再生成できる旨も添えると判断しやすい。

### 全消し系キャッシュ
`uv cache clean`（uv キャッシュ全消し）、`go clean -modcache`（Goモジュールキャッシュ全消し）、`~/.cache/huggingface`、`~/.cargo/registry` の削除。いずれも再取得コストがそれなりにある（次回ビルド・実行が遅くなる）ので、そのトレードオフを一言添えてから聞く。

## ステップ5: スコープ外の大物

`measure.sh` の「スコープ外」セクションで `~/.screenpipe` と `~/.ollama` のサイズを見せる。これらは開発ツールキャッシュではなく、それぞれ画面記録データとローカルLLMモデルという性質の異なるデータなので、削除判断はこのスキルの外に置く。「サイズが大きいので気になれば手動で確認してください」と伝えるだけで、削除の提案や実行はしない。

## ステップ6: 最終測定とログ記録

`scripts/measure.sh` をもう一度実行し、ステップ1の空き容量と比較する。`~/.local/state/storage-clean/history.log`（ディレクトリが無ければ作成）に1行追記する。

```
<YYYY-MM-DD>	<実行前空き>	<実行後空き>	<何を消したかの短いメモ>
```

最後に「今回で空きが何GB増えたか」を一言でまとめて終了する。

## Nix 自動GCの確認について

`measure.sh` の出力に `org.nixos.nix-gc.plist` の有無が出る。無い場合は「macbook host に `nix.gc.automatic` がまだ宣言されていないかもしれません」と伝えるだけでよい。GC の設定変更や `nix switch` の実行はこのスキルの仕事ではない（宣言的な nix 設定として別途管理されている）。
