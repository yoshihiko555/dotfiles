# context-prune

AI が既定で読む場所からノイズを外すスキル。判定の問いは 1 つ:

> **この記述を消したら、読んだ AI / 人が間違えるようになるか。** 間違えないならノイズ。

消した情報はどこにも移設しない。ADR や docs へ移すと、そこが新しいノイズ源になるため。
代わりに git 履歴に残し、コミットメッセージの要約（Phase 5）で後から `git log` で探せるようにする。

判定基準の詳細と例は [references/criteria.md](references/criteria.md) にある。Phase 1 の前に読むこと。

---

## モード判定

- **引数が空、または `diff`** → **diff モード**（作業ツリー）
  `git diff HEAD` の**追加行**だけが候補。変更がなければその旨を伝えて終了する。
- **ブランチ名 / コミット ref** → **diff モード**（範囲）
  `git diff <ref>...HEAD` の**追加行**だけが候補。
- **パス、または `all`** → **棚卸しモード**
  指定範囲の追跡ファイル全体が対象。

diff モードでは、変更したファイルにもともとあったノイズは対象外とする
（それを拾い始めると棚卸しモードと区別がなくなる）。既存のノイズは棚卸しモードで扱う。

---

## Phase 0: 規約と対象の確定

1. **作業ツリーの状態を記録する**: `git status --porcelain` を控える。
   Phase 5 で「スキルが編集したもの」と「もともとの未コミット変更」を区別するため。
2. **プロジェクトの規約を読む**: `AGENTS.md` / `CLAUDE.md` / `CONTRIBUTING*` /
   docs 内のコーディング規約・ADR テンプレート。コメント・文書・ADR・コミットの方針があれば、
   [references/criteria.md](references/criteria.md) の既定より**規約を優先する**。
   既定と食い違う点はレポート冒頭に書く。
3. **対象外を先に報告する**:
   - 追跡されていないファイル（`git ls-files` で追跡ファイルに限定する）、
     生成物・vendor・ロックファイル・ビルド出力
   - 経緯を書くこと自体が目的の文書: CHANGELOG、ADR の本文、議事録、リリースノート
   - 計測結果そのものが目的の文書（ベンチマーク結果など）
   - テストのフィクスチャ・サンプルデータ
   - 隣接スキルの領分: コメントアウトされたコード（dead-code-audit）、
     実装と文書の乖離（doc-drift）、コンテキストファイル 1 本ごとの冗長さ（config-analyze）
4. **生成・取り込みの仕組みを検出し、生成側を外す**:
   1 つの原本から複数ファイルを作る同期タスク（Taskfile / Makefile / scripts）、
   `@path` 形式のインポート、シンボリックリンク、`DO NOT EDIT` / `AUTO-GENERATED` の目印。
   原本と生成物を「重複」と誤検出しないため。生成物にノイズがあれば原本側で指摘する。
5. 棚卸しモードでは**対象ファイル数を報告してから**始める。

---

## Phase 1: 検出と分類

対象ごとの観点（詳細と例は criteria.md）:

- **コードコメント**: 経緯・履歴、コードの言い換え（What / How の繰り返し）、
  由来・実測値の注記。Why not、非自明な Why、警告、ディレクティブは残す。
  コード内の TODO / FIXME は対象外。
- **README / docs**: 重複、経緯・変更履歴の散文、陳腐化した計画・TODO、冗長な言い回し。
- **コンテキストファイル**: ファイル間・docs との重複、陳腐化した記述。
- **ADR**: 置き換え済み ADR の status、索引（`DECISIONS.md` 等）と本文の status の食い違い、
  置き換え済み ADR への参照。**本文のセクションは編集しない。**
  編集してよいのはヘッダのステータス行・置換関係欄と索引だけ。
  status の語彙はプロジェクトの ADR テンプレートに合わせ、表記の統一は提案しない。

各候補を 3 階層に分ける:

| 階層 | 定義 | 承認 |
| --- | --- | --- |
| **T1** | 消しても情報が何も失われない（言い換え、正本が明らかな完全重複） | 一括 |
| **T2** | 情報が消える、または書き換えを伴う（経緯、実測値、陳腐化、言い回し、ADR の状態） | 個別 |
| **T3** | ノイズか判断がつかない。判断材料だけを示し、結論は出さない | 適用しない |

迷ったら低い方（T1 → T2 → T3）に置く。T1 は一括承認されるので、誤検出のコストが最も高い。

候補には**階層をまたいだ通し番号**を振る。反証で T1 → T2 に降格しても番号が変わらないようにし、
ユーザーの「T1 全部、あと 3 と 5」を安定させるため。

### 対象が大きい場合

棚卸しモードで対象が数十ファイルを超えるときは、ファイル単位の検出をディレクトリごとに
サブエージェントへ分割して並列に行う。各サブエージェントには criteria.md のパス、
Phase 0 で読んだ規約の要約、対象外の一覧を渡す。

**重複の検出は分割しない。** ファイルをまたぐ比較なので、docs とコンテキストファイルの一覧を
手元に集めて、メインのコンテキストで行う。

---

## Phase 2: T1 の反証

T1 候補を、**新しいコンテキストのサブエージェント**に渡して反証させる。
`fork` は使わない（検出時の理由付けを引き継ぐと、同じ判断を追認するだけになる）。

- 渡すもの: 候補ごとの `path:line`、該当箇所と前後の文脈（周辺のコード・段落）、
  criteria.md の T1 定義。
- 問い: 「これを消すと、読んだ AI / 人が間違えるようになるか」「消える情報はないか」。
- 反証された候補は T2 に降格し、降格理由を添える。

サブエージェントを使えない環境（Codex / Antigravity など）では反証できない。
その場合は T1 を作らず、すべて T2 として扱い、その旨をレポートに書く。

---

## Phase 3: レポート

会話に出す。ファイルには書き出さない。

```
## context-prune レポート（<モード>: <範囲>）

適用した基準: <規約ファイル / 既定（criteria.md）> と、既定との食い違い
対象外: <Phase 0 の一覧>
生成物として外したもの: <原本 → 生成物>

### T1（一括承認できる）
[1] path:line — <種別>
    現状: <該当箇所>
    提案: 削除 | 置換「...」

### T2（個別に承認する）
[2] path:line — <種別>
    現状: <該当箇所>
    提案: 削除 | 置換「...」（書き換えは差分で示す）
    消える情報: <要約。実測値なら値をそのまま>
    降格理由: <反証で降格した場合のみ>

### T3（判断材料のみ）
[3] path:line — <迷っている点>
    判断材料: ...

### 未確認の領域
<読まなかった範囲、確かめられなかった点、判断を保留した箇所>
```

`path:line` の行番号は `grep -n` か Read の出力で確かめてから書く。記憶で書くとずれ、
ユーザーが別の行を見て承認することになる。

最後に承認の返し方を 1 行で示す（例: 「T1 全部、T2 は 2 と 5」）。
**確認していないことを「ノイズなし」と報告しない。**

---

## Phase 4: 承認と適用

ユーザーの返答を待つ。承認された項目だけを Edit で直す。

- T3 は直さない。ユーザーが番号を指定して承認した場合のみ直す。
- 削除で空行の連続・空のコメントブロック・崩れたインデントが残らないよう整える。
- プロジェクトに整形コマンドがあれば（規約・タスクランナーで確認）、編集したファイルに対して実行する。

---

## Phase 5: コミット

### メッセージの形式

プロジェクトのコミット規約（言語・prefix）に従う。本文には必ず `Pruned:` セクションを置く。
後から `git log --grep "Pruned:"` で探せるようにするため。

```
<規約に沿った件名>

Pruned:
- path — <種別>: <消した内容の要約>
- path — 実測値: <値をそのまま書く>
```

**実測値を含む記述を消した場合は、値をそのまま本文に書く。** 要約で値を落とすと、
「git 履歴に残して探せるようにする」という前提が崩れる。行番号はずれるので書かない。

### コミットの進め方

- **編集したファイルに、Phase 0 で記録した未コミット変更がない場合**:
  編集したファイルだけを `git add <path>...` で stage する（`-A` は使わない）。
  メッセージ案を示し、承認されたらコミットする。
- **編集したファイルに、もともとの未コミット変更がある場合**（引数なしの diff モードでは必ずこうなる）:
  消した内容はまだ git 履歴にない。コミットするとユーザーの作業中の変更も一緒に入る。
  `Pruned:` ブロックを「次のコミットに含める文面」として示し、
  一緒にコミットするか、ユーザーが自分でコミットするかを確認する。
- pre-commit フックが落ちたら、原因を直して stage し直す。`--no-verify` は使わない。
- ブランチ・PR の運用はプロジェクトの規約に従う。

---

## 実行上の注意

- 消すだけで移設しない。ADR や docs への追記は提案しない。
- ADR の本文、CHANGELOG、生成物は編集しない。
- Codex / Antigravity から実行する場合、`allowed-tools` と `disable-model-invocation` は
  Claude Code 固有の指定なので効かない。反証は Phase 2 のフォールバックに従う。
