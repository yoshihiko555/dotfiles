# context-prune 判定基準（既定）

プロジェクトの規約に方針があれば、そちらを優先する。ここは規約がない場合の既定。

## 目次

1. 判定の軸
2. コードコメント
3. README / docs
4. コンテキストファイル
5. ADR
6. 階層の判定

---

## 1. 判定の軸

**剪定テスト**: この記述を消したら、読んだ AI / 人が間違えるようになるか。間違えないならノイズ。

情報の置き場所（t-wada 氏の整理に基づく）:

| 情報 | 置き場所 |
| --- | --- |
| How（どう動くか） | コード |
| What（何をするか） | テスト |
| Why（なぜそうしたか） | コミットログ |
| Why not（なぜ他の方法を採らないか） | コードコメント |

ただし**非自明な Why はコメントに残す**。コードだけを読んだ AI が「もっと良い書き方がある」と
判断して壊すのを防ぐガードになるため。コミットログに送るのは、読み手の判断を左右しない Why と経緯。

## 2. コードコメント

### ノイズ

**言い換え（T1）**: コードを読めば分かることを繰り返しているだけ。

```python
# ユーザー一覧を取得する
users = fetch_users()
```

```ts
// increment counter
count++;
```

**経緯・履歴（T2）**: いつ・何から変えたか。git 履歴の領分。

```nix
# 以前は Homebrew で入れていたが 2026-08 に Nix へ移行
```

```go
// Changed from sync.Mutex to RWMutex in PR #123
```

**由来・実測値（T2）**: どこから持ってきたか、測ったらどうだったか。
実測値は過去との比較資料になるため、消すときは値をコミットメッセージにそのまま残す。

```lua
-- 旧 WezTerm の設定から移植
-- 実測で起動 1.5s → 0.25s
```

**Why と経緯が混ざったもの（T2・書き換え）**: Why の部分を残し、経緯の部分だけ削る。

```python
# 2026-05 に障害が出たので、ここでロックを取る（並行実行で残高が二重に減るため）
# ↓
# 並行実行で残高が二重に減るため、ここでロックを取る
```

### 残すもの（候補にしない）

- **Why not**: `# リトライしない: 決済 API は冪等でないため二重課金になる`
- **非自明な Why**: `# macOS の BSD sed は -i に空文字の引数が要る`
- **警告**: `# この 2 行の順序を入れ替えると初期化前に参照される`
- **ディレクティブ**: `# noqa`、`# type: ignore`、`// eslint-disable-next-line`、
  `// @ts-expect-error`、`# shellcheck disable=...`、`//go:build`、`# -*- coding -*-`、shebang
- **ライセンス / 著作権ヘッダ**: `SPDX-License-Identifier` など
- **外部仕様へのリンク**: 挙動の根拠になっている RFC・issue・ドキュメントの URL

### 対象外

- コメントアウトされたコード（dead-code-audit の領分）
- TODO / FIXME / HACK（まだ有効な可能性があり、自動判定できない）

### 迷うもの（T3）

- **公開 API の docstring / JSDoc**: シグネチャの言い換えに見えても、IDE のホバーや
  ドキュメント生成で使われている可能性がある。
- **Why か言い換えか判断がつかないもの**: ドメイン知識がないと自明かどうか決められない。

## 3. README / docs

### 重複

同じ内容が複数の文書にある。

- **正本が明らかなら T1**: 一方がもう一方の完全な複製で、正本が決まっている
  （他の文書からのリンク先になっている、など）。複製側を正本への参照に置き換える。
- **どちらを正本にするか判断が要るなら T2**。
- 部分的な重複（同じ手順を別の文脈で説明している）は T2。

### 経緯・変更履歴の散文（T2）

```markdown
当初は Redis でセッションを管理していたが、運用コストの問題から JWT に移行した。
現在は JWT を使っている。
↓
セッションは JWT で管理する。
```

### 陳腐化した計画・TODO（T2）

「今後対応予定」「移行中のため〜」と書かれているが、git log・コードを見ると完了している、
または放棄されている。**完了・放棄を確かめた根拠（コミット・ファイル）を添える。**
確かめられなければ T3。

### 冗長な言い回し（常に T2）

文体が変わるので、一括承認にはしない。必ず差分で示す。

- 「〜することができます」→「〜できます」
- 「このセクションでは〜について説明します」のような前置き
- 同じ段落内での言い換えの繰り返し

## 4. コンテキストファイル

対象は `CLAUDE.md` / `AGENTS.md` / `GEMINI.md` / `SKILL.md` / `.cursor/rules` などの、
エージェントが毎回読むファイル。**ファイル 1 本ごとの冗長さは見ない**（config-analyze の領分）。

- **ファイル間の重複**: 同じルールが複数のコンテキストファイルに書かれている。
  `@path` インポートや同期タスクで生成されたものは重複ではない（Phase 0 で外す）。
- **docs との重複**: docs の内容をコンテキストファイルに丸ごと再掲している。docs への参照に置き換える。
- **陳腐化した記述**: 完了した移行作業の注意書き（「〜は移行中なので触らない」）など。
  完了を確かめた根拠を添える。

## 5. ADR

**本文のセクション（背景・選択肢・決定・結果など）は編集しない。** 決定時点の記録なので、
後から書き換えると記録としての価値が失われる。編集してよいのはヘッダのステータス行・
置換関係欄と、索引（`DECISIONS.md` など）だけ。いずれも T2。

- **置き換え済み ADR**: 後の ADR が同じ問いに別の結論を出しているのに、status が「採用」のまま。
  ステータスを置換 / 廃止に更新し、置換関係欄と索引も合わせる。
  語彙はプロジェクトの ADR テンプレートに従う（例: 置換 / 廃止 / Superseded / Deprecated）。
- **索引と本文の食い違い**: 索引の status と本文の status が違う。
  どちらが正しいかは本文と後発の ADR から判断し、根拠を添える。
- **置き換え済み ADR への参照**: コンテキストファイル・docs・コメントが、置き換え済みの ADR を
  現行の決定として参照している。後発の ADR への参照に置き換える。

表記の揺れ（「採用」と「accepted」の混在など）は提案しない。

## 6. 階層の判定

| 階層 | 定義 | 典型例 |
| --- | --- | --- |
| T1 | 消しても情報が何も失われない | 言い換えコメント、正本が明らかな完全重複 |
| T2 | 情報が消える、または書き換えを伴う | 経緯、由来、実測値、陳腐化、言い回し、ADR の状態、Why と経緯の分離 |
| T3 | ノイズか判断がつかない | 公開 API の docstring、Why か言い換えか曖昧なもの、根拠を確かめられない陳腐化 |

迷ったら低い方に置く。T1 は一括承認されるため、誤って T1 に入れたときのコストが最も高い。
