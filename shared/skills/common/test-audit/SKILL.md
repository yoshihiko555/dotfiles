# test-audit

**スコープ**: 呼び出し時に指定されたパス。指定がなければリポジトリ全体。

テストを**追加も修正もしない**。現状を可視化するレポートのみを出力する。
「どう直すか」ではなく「**今どうなっているか**」を明らかにするのが目的。

---

## Phase 0: 構成の把握（推測しない）

1. `git ls-files` でソースとテストの配置規約を特定する。
   （`tests/` 配下か、`*_test.go` か、`*.spec.ts` か、co-location か）
2. テストランナーと設定を特定する（マニフェスト・設定ファイルから）。
3. **対象外を先に報告する**: 生成物、ベンダー、別リポへ移設済みの領域、
   E2E など別系統で管理されているもの。
4. ソースファイル数・テストファイル数・概算行数を報告してから本編に入る。

対象が大きい場合は優先度の高いサブツリーに絞り、
**絞った理由と対象外にした範囲を明記する**。

## Phase 1: 機械的に測れるものはツールに測らせる

**実在するものだけ**を実行し、結果を引用する。未インストールなら実行せず
「未実行」と記録する。**勝手に install しない。**

- カバレッジ計測が設定済みなら実行する
  （`pytest --cov`、`go test -cover`、`npx vitest run --coverage` 等）
- テストが現在通るかを確認する。落ちているテストがあれば、それ自体を報告する

計測できた場合は**その数値を根拠として引用**し、できなければ
Phase 2 のファイル対応による推定であることを明記する。

## Phase 2: 5つの観点で検査

### 1. カバレッジ欠落

対応するテストファイルが**存在しない**ソースファイルを列挙する。
判定は単なるファイル名の対応ではなく、
**そのソースの export がどのテストからも import されていないか**を
grep で相互参照して確認する。

### 2. 意味のないテスト

- 実質的に何も検証していないテスト（真偽値の存在確認だけ、など）
- 入力がわずかに違うだけで実質同一のテスト
- モックが厚すぎて、モックの挙動しか検証していないテスト

### 3. 脆いテスト

実装詳細に密着しているもの。

- 非公開の内部実装を直接検証している
- 整形の変更で壊れる、出力文字列の完全一致検証
- 実行順序や時刻に暗黙に依存している

### 4. 重複した setup

複数のテストファイルにまたがる、同一またはほぼ同一の
セットアップ/ティアダウン処理。共通ヘルパーに切り出せる候補。

### 5. エッジケースの欠落

明らかにエラー経路やエッジケース（null、空配列、境界値、ネットワーク失敗など）
を持つ関数に対して、ハッピーパスしかテストされていないもの。

## Phase 3: 誤検出の除外（必ず適用）

- **意図的に薄いテスト**: スモークテスト、型レベルの検証、
  契約テストの一部として成立しているもの
- **生成コード・定型コード**にテストがないのは通常問題ない
- **統合テスト側でカバーされている**ユニット未テストのコード
  （統合テストの存在を確認してから判定する）
- 外部ライブラリの薄いラッパー

除外できない場合は「要判断」として理由を添える。

---

## 出力

観点ごとにまとめ、各項目を `[HIGH|MEDIUM|LOW] 説明 — path:line` の形式で。
1観点あたり最大15件に絞り、絞った場合は総件数も併記する。

重要度の目安:

- **HIGH**: 壊れても気づけない箇所（カバレッジ欠落のうち、ロジックが厚いもの）
- **MEDIUM**: 保守コストになっているもの（脆いテスト、重複 setup）
- **LOW**: 整理すると綺麗になる程度

末尾に必ず:

- **サマリ**: ソース/テストのファイル数、カバレッジ（計測できた場合のみ）
- **未確認の領域**: 実行できなかったコマンド、読まなかった範囲、判断を保留した箇所。
  **確認していないことを「問題なし」と書かないこと。**

---

## 実行上の注意

- テストファイルを一切変更しない。レポートのみ。
- 「テストを追加すべき」という一般論は書かない。
  **具体的にどのファイルのどの関数か**を示す。
- 自分が書いたテストを同一セッションで監査すると判定が甘くなる。
  新しいセッション、またはサブエージェント経由で実行する。
