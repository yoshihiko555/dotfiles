# dead-code-audit

**スコープ**: 呼び出し時に指定されたパス。指定がなければリポジトリ全体を対象とし、
Phase 0 で除外候補を報告してから進める。

「これは改善すべきか」ではなく「**これは存在すべきか**」を最初の問いとする。
リファクタ提案はしない。削除・変更も行わない。レポートのみを出力する。

---

## Phase 0: スコープの確定（推測しない）

1. `git ls-files` を実行し、追跡ファイルの構成を把握する。
2. 以下を**除外候補**として列挙し、除外してよいか判断根拠とあわせて**先に報告する**。
   - ベンダーディレクトリ、lock ファイル、ビルド出力、コード生成の出力先
   - 別リポジトリへ移設済み、または削除予定のディレクトリ
     （README / 計画ファイル / 最終更新日 / コミット履歴から推定する）
   - 同一内容の複製（ビルド成果物としてのミラー、facet build の出力など）
3. エントリポイントを特定する。パッケージマニフェスト・タスクランナー設定・
   CI 設定・フック登録・プラグイン登録・テストから拾う。

> 除外候補の報告を飛ばさないこと。どのリポジトリにも「すでに死んでいる領域」があり、
> そこを本気で監査すると出力の大半が無駄になる。

## Phase 1: 言語のツールに測らせる（推測で埋めない）

リポジトリのスタックを検出し、**実在するものだけ**を実行してその結果を引用する。
未インストールなら実行せず「未実行」と記録する。**勝手に install しない。**

| スタック | コマンド |
| --- | --- |
| Python | `uvx ruff check --select F401,F841` / `uvx vulture <path>` |
| TS / JS | `npx knip` / `npx ts-prune` / eslint の unused 系ルール |
| Go | `go vet ./...` / `staticcheck ./...` |
| Rust | `cargo build` の `dead_code` 警告 |

**ツールが測った結果と、読解による推測を、レポート上で必ず分けること。**

## Phase 2: ツールで測れない領域

ここが LLM の担当範囲。

1. どこからも参照されていないファイル。import だけでなく、
   設定ファイル・ドキュメント・タスクランナー・CI からの参照も grep で確認する。
2. 設定やドキュメントから参照されているが**実在しないパス**（逆向きの死）。
3. 役目を終えた feature flag、`coming soon` 的なプレースホルダ。
4. コメントアウトされたコードブロック。
5. 同じことをする関数が複数ある場合の、生きている側の特定。

## Phase 3: 誤検出の除外（必ず適用）

以下は「未使用に見えても死んでいない」。除外するか、除外理由を添えて T3 に回す。

- 動的ディスパッチ・リフレクション・文字列経由の参照
  （`getattr`、DI コンテナ、ルーティング表、シグナル/イベント登録）
- 外部に公開している API やライブラリのエクスポート
- テストのフィクスチャ、型定義のみのファイル
- OS / CI / cron / フックから呼ばれるエントリポイント

---

## 出力

3階層に分け、`path:line` を付けて報告する。

- **T1**: 参照ゼロを機械的に確認済み。削除して安全。
  **確認に使ったコマンドを併記する。**
- **T2**: 削除できそうだが確認が要る。
  **何をどう確認すれば判定できるかを書く。**「要確認」だけで終わらせない。
- **T3**: 判断が必要。判断材料を示し、**結論は出さない**。

末尾に**未確認の領域**を必ず列挙する。実行できなかったコマンド、読まなかった範囲、
判断を保留した箇所。**確認していないことを「問題なし」と書かないこと。**

---

## 実行上の注意

- ファイルは一切変更しない。レポートのみ。
- 対象が大きい場合は、Phase 0 で優先度の高いサブツリーに絞り、
  絞った理由と対象外にした範囲を明記する。
- 自分が書いたコードを同一セッションで監査すると判定が甘くなる。
  可能なら新しいセッション、またはサブエージェント経由で実行する。
