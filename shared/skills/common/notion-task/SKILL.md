# notion-task

## 目的

相談・設計・デバッグなどの会話をした後に、その内容を Notion のタスクDBへ残す。
狙いは2つある。

- **取りこぼし防止** — 会話で決まった「やること」を、その場で着手しないまま流さない
- **後日の再開** — 「今はやらないが後でやりたい」ものを、後から文脈ごと思い出せる形で保存する

後者があるので、タスク名だけ登録して終わりにはしない。数週間後の自分が読んで
「なぜこれをやろうと思ったのか」を復元できる本文を必ず書く（→ [ページ本文](#ページ本文)）。

## 前提

- 登録先は Notion の **タスクDB（`T A S K`）**。ID・プロパティ定義は `references/notion-schema.md` を参照する
- 操作には **Notion MCP** を使う。ツール名のプレフィックスは環境で異なる
  （Claude Code: `mcp__claude_ai_Notion__notion-*` など）。以下では論理名（`search` / `fetch` /
  `create-pages` / `query-data-sources`）で書く
- Notion MCP が利用できない環境では、勝手に別手段（REST API を curl 等）を試さず、
  MCP を有効化するようユーザーに案内して中断する。認証情報を新たに要求しないため

## 最重要: タスクテンプレートを必ず使う（作成は2段階）

タスクDBのページは、アイコンがチェックボックス（`checkmark-square_lightgray`）で統一されている。
これは絵文字ではなく Notion 組み込みアイコンなので、`icon` 引数では再現できない。
**`create-pages` に `template_id` を渡す**ことでのみ引き継がれる。

そして `create-pages` は **`template_id` と `content` を同時に受け付けない**
（`Cannot specify both 'content' and 'template_id'` で 400 になる）。
そのため作成は必ず次の2段階に分ける。

```
# 1) テンプレート適用でページを作る（content は渡さない）
create-pages(
  parent = { data_source_id: <タスクDBのデータソースID> },
  pages  = [{ template_id: <タスクテンプレートのページID>, properties: { "タスク名": "..." } }]
)
# → 返却された page id / url を控える

# 2) 本文を追記する
update-page(
  page_id = <1で得た id>,
  command = "insert_content",
  position = { type: "end" },
  content = "## 背景\n..."
)
```

守るべき点は次の2つ。

- **`icon` を指定しない。** `create-pages` でも `update-page` でも渡さない。
  指定するとテンプレートのアイコンを上書きしてしまう。絵文字を選びたくなっても選ばない。
  既存タスクと見た目が揃わなくなるのが唯一かつ致命的な問題
- **テンプレートの既定値を尊重する。** ステータス=`待ち` / GTD種別=`INBOX` / 優先度=`低` は
  テンプレート側で設定済み。プロパティに含めず、テンプレートに任せる

登録後、作成したタスクを1件 `fetch` してアイコンが `checkmark-square_lightgray` になっているか確認する。
万一テンプレートが適用されていなければユーザーに報告する（黙って別のアイコンで代用しない）。

## 実行フロー

### ステップ1: 対象範囲を決める

ユーザーが対象を明示していれば（「さっきの認証周りの話」など）それに従う。
明示がなければ、直近の議論のうち「結論が出たが着手していないもの」を対象にする。

会話がまだ結論に至っていない場合は、無理にタスク化せず「まだ方針が固まっていないが、
現時点の案でタスク化するか」を確認する。

### ステップ2: 候補を抽出し、粒度を判断する

会話から「やること」を抽出し、次の観点で粒度を決める。粒度は会話ごとに変わるので、
機械的に分けず毎回考える。

**1件にまとめる方が良い**
- 成果物が1つで、分割しても並行して進められない
- 途中で止めても意味のある中間成果が残らない
- 分割すると各タスクの説明文がほぼ同じ内容になる

**複数に分割する方が良い**
- それぞれ独立に着手・完了でき、片方だけ後回しにできる
- 成果物が別（例: 実装 / ドキュメント / 検証環境の準備）
- 着手できるタイミングが違う（例: 先方の返答待ちが挟まる）

**分割したうえで親子にする**
- 分割はしたいが、全体として1つのまとまりとして進捗を追いたい場合
- 親タスク1件を作り、子タスクの `親アイテム` プロパティに親を設定する
- 子が2件以下なら、親を作らずフラットに並べた方が扱いやすいことが多い

### ステップ3: プロジェクトの候補を探す

会話の対象（リポジトリ名、サービス名、話題の主語）をもとに
PROJECT DB（`references/notion-schema.md` 参照）を `query-data-sources` または `search` で検索する。

- 妥当な候補が見つかれば、ステップ4の確認に「プロジェクト: ○○ でよいか」を含める
- 見つからなければ未設定のまま進める。新しいプロジェクトを勝手に作らない

### ステップ4: 重複を確認する

タスクDBを `query-data-sources` で検索し、同等のタスクが既にないか確認する
（完了・中断のものは除外する。クエリ例は `references/notion-schema.md`）。
確認は**ユーザーへの提示より前**に行う。既存タスクの有無は、ユーザーが
「登録する／既存を更新する／やめる」を判断するための材料になるため。

### ステップ5: ユーザーに確認する（必須）

登録前に必ず確認を取る。会話から起こしたタスクは、こちらの解釈がズレていることがあるため。
提示するのは以下。

- 番号付きリストで、各タスクの **タスク名** と **本文の要旨（1〜2行）**
- 粒度の判断（「1件にまとめました」「3件に分割し、親子にしました」）とその理由
- プロジェクト候補（ステップ3で見つかった場合）
- 重複しそうな既存タスク（ステップ4で見つかった場合）とそのリンク
- 期限日・GTD種別・優先度を変更する提案がある場合はその内容

選択UI（`AskUserQuestion` / `ask-survey` など）が使える環境では複数選択で提示し、
「すべて登録」「登録しない」も選べるようにする。使えない環境では番号を返してもらう。

ユーザーが選ばなかった項目は登録しない。文言や粒度の修正を求められた場合は、
反映してからもう一度確認する。

### ステップ6: 登録する

親子構造にする場合は **親を先に作成し、返ってきたページURLを子の `親アイテム` に設定する**。

設定するプロパティは以下に限る。ここに書かれていないものはテンプレートに任せる。

| プロパティ | 扱い |
|---|---|
| `タスク名` | 必須。動詞で終わる形にする（例: 「〜を調査する」「〜を移行する」） |
| `プロジェクト名` | ステップ5で合意した場合のみ設定。リレーションなのでページURLの**配列**で渡す |
| `親アイテム` | 子タスクにのみ設定。親のページURLを**配列**で渡す |
| `期限日` | **勝手に設定しない。** ユーザーが明示した場合のみ（`date:期限日:start` 形式） |
| `GTD種別` | 原則テンプレート既定（`INBOX`）。ユーザーが「後日やる」等を明示した場合のみ変更 |
| `優先度` | 原則テンプレート既定（`低`）。ユーザーが明示した場合のみ変更 |
| `ステータス` | 常にテンプレート既定（`待ち`）。設定しない |
| 上記以外 | 設定しない（開始日 / ポモロード / K E Y - R E S U L T など） |

プロパティを設定したら、続けて `update-page` の `insert_content` で本文を追記する
（→ [ページ本文](#ページ本文)）。

### ステップ7: 報告する

作成したタスクを一覧で提示する。

- タスク名 + ページURL（親子の場合は階層が分かる形で）
- 候補に挙げたが登録しなかったものがあれば、それも明示する
- ステップ5で重複が見つかっていた場合は、その扱いの結果

## ページ本文

テンプレート本文は空なので、`update-page` の `insert_content` で以下を追記する。
「後日の再開」が目的なので、会話を読み返さなくても文脈が復元できる密度にする。
薄すぎるより多少厚い方が良い（ページが重くなるのは許容範囲）。

```markdown
## 背景

なぜこのタスクが必要になったか。どういう問題・きっかけがあり、会話でどんな議論を経て
この結論に至ったか。5〜10行程度。「〇〇の実装中に△△が問題になった」のように、
状況が思い出せる具体名（ファイル名・エラー・数値）を入れる。

## 検討内容

会話で出た選択肢と比較。特に **却下した案とその理由** は必ず残す。
後から「これ試したっけ？」を防げるのがここの価値。
該当する議論がなければこのセクションごと省略する。

- 案A: 〜 → 採用。理由は〜
- 案B: 〜 → 却下。理由は〜

## 完了条件

- [ ] 何ができたら完了か。検証可能な形で書く

## 参考

- 関連ファイルパス、コミットハッシュ、URL など
- 該当がなければこのセクションごと省略する
```

事実の捏造はしない。会話に出ていない理由・数値・リンクを補わない。
不明な点は空欄にするか、確認する。

## 検証チェックリスト

- [ ] `create-pages` に `template_id` を渡し、`content` と `icon` は渡していない
- [ ] 本文は `update-page` の `insert_content` で別途追記している
- [ ] 作成したタスクのアイコンが `checkmark-square_lightgray` になっている（`fetch` で確認）
- [ ] ステータス / GTD種別 / 優先度 が テンプレート既定（待ち / INBOX / 低）になっている
- [ ] 期限日をユーザーの明示なしに設定していない
- [ ] 登録前にユーザーの確認を取っている
- [ ] 各タスクの本文に「背景」と「完了条件」が入っている
- [ ] 親子構造にした場合、子の `親アイテム` に親が設定されている
- [ ] 作成結果をリンク付きで報告している
