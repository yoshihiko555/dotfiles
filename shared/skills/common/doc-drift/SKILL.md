# doc-drift

ドキュメントも実装も**変更しない**。乖離の一覧のみを出力する。

---

## モード判定

- **引数が空、`diff`、またはブランチ名** → **diff モード**
  `git diff` の範囲の実装変更に対して、**追従できていないドキュメント**を探す。
  既存の乖離は対象外。
- **引数がパス、または `all`** → **リポジトリモード**
  ドキュメント全体と実装を照合する。

diff モードを既定とする。リポジトリモードは初回の棚卸し向け。

## Phase 0: 対象の確定

1. ドキュメントの所在を特定する。
   `README*`、`docs/`、`CONTRIBUTING*`、`AGENTS.md` / `CLAUDE.md`、
   パッケージ説明、各ディレクトリの README。
2. **対象外を先に報告する**: 自動生成ドキュメント、CHANGELOG（履歴なので乖離しない）、
   外部からコピーしたライセンス類、別リポへ移設済みの領域。
3. リポジトリモードではファイル数を報告してから始める。

---

## Phase 1: 照合する観点

**公開面に絞る。** 内部実装の説明の細かい食い違いは対象としない。

### 1. 手順・コマンドの実在性

ドキュメントに書かれたコマンドが実際に動くか。

- タスクランナー / スクリプトに**そのタスクが存在するか**
  （`Taskfile.yml`、`package.json` の scripts、`Makefile` 等と突合）
- 参照しているファイルパスが**実在するか**
- インストール手順が現在の依存定義と整合しているか

### 2. 設定項目

ドキュメントに載っている設定キー・環境変数が実装側に存在するか。
**逆向きも見る**: 実装が読んでいるのにドキュメントにない環境変数。

### 3. 公開インターフェース

エクスポートされている関数・CLI のサブコマンド・API エンドポイントが、
ドキュメントの記述と一致しているか。**削除済みのものが残っていないか。**

### 4. 内部リンク

ドキュメント間のリンク、ドキュメントからコードへのリンクが切れていないか。

### 5. ディレクトリ構成図

README に構成図がある場合、実際のディレクトリと一致しているか。
（**最も腐りやすい箇所**）

---

## Phase 2: 除外（必ず適用）

- **意図的な簡略化**: 「例えば」「〜など」と書かれた例示は網羅性を求めない
- **将来計画**: ロードマップ、TODO として明示されているもの
- **文体・表現の好み**: 乖離ではない
- **CHANGELOG / ADR / 議事録**: 過去の記録なので実装と一致しなくて当然

「乖離しているが直すべきでない」ものは、理由を添えて別枠にする。

---

## 出力

乖離ごとに:

```
[重要度] path:line — 乖離の内容
  ドキュメントの記述: ...
  実装の実態: ...
  確認方法: ...
```

重要度の目安:

- **HIGH**: 従うと失敗する手順、存在しないコマンド・パス、削除済み機能の記載
- **MEDIUM**: 記述はあるが古い、実装にあるのに未文書化の公開要素
- **LOW**: 構成図のずれ、表記の不整合

末尾に必ず **未確認の領域** を列挙する。読まなかったドキュメント、
実行して確かめられなかったコマンド、判断を保留した箇所。
**確認していないことを「問題なし」と報告しない。**

---

## 実行上の注意

- ドキュメントもコードも変更しない。
- 「ドキュメントを充実させるべき」という一般論は書かない。
  **具体的にどの記述がどう食い違っているか**だけを報告する。
- 実在性の確認は grep / ls で**実際に確かめる**。記憶で判断しない。
