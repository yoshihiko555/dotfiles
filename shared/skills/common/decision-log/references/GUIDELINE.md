# ADR 執筆ガイドライン

ADR は「なぜその方式を選んだか」を、実装が変わっても読み返せる形で残す文書。
作業の記録や実装の説明書ではない。

- 書き手（decision-log スキル）と点検役（点検用のサブエージェント）は、どちらもこのファイルを基準にする
- 規約は、実際に ADR を直した指摘から足す。机上で増やさない
- 既存の ADR は書き直さない。この規約は新しく書く ADR と、索引・書式の統一に適用する

強度の意味:

- **MUST**: 必ず守る
- **SHOULD**: 原則守る。外すときは理由を ADR か点検結果に書く

## 判定の問い

迷ったら次の 2 つで判断する。

1. **置換テスト**: 決めた実現方式を別の方式へ置き換えたとき、この記述を書き換える必要があるか。
   必要なら ADR ではなく、コード・コメント・領域の docs・コミット本文に置く
2. **反転テスト**: この数値・経緯が逆の結果だったら、決定は変わったか。
   変わるなら判断の根拠として ADR に残す。変わらないなら作業の記録なのでコミット本文に置く

## 置き場所の早見表

| 内容 | 置き場所 |
|---|---|
| 今決める理由、制約、判断の根拠になった実測・経緯 | ADR「背景」「選択肢」 |
| 採る方式と適用範囲 | ADR「決定」 |
| 成功の条件と最終的な結果 | ADR「検証」（数行） |
| 段階ごとの計測値、試行錯誤の順序、作業の経過 | コミット本文 |
| 移行の手順・タスク・進捗 | タスク管理・コミット本文 |
| 実装の詳細（関数名・フラグ・ファイル構成・設定キー） | コード・コメント・領域の docs |
| 採用後の版更新や前提の変化 | コミット本文（決定が変わるなら新しい ADR） |

## 規約

### A. 範囲

- **A-1 MUST**: 1 本の ADR に書く決定は 1 つにする。作業中に別の決定が生まれたら、別の ADR にして「関連」で結ぶ
- **A-2 MUST**: 移行の手順・進捗・タスク表・チェックボックス・担当・期限を書かない。完了すれば古くなる情報だから
- **A-3 SHOULD**: 決定は、実装の自由度を奪わない粒度で書く（置換テスト）。
  関数名・フラグ・設定キーは、それ自体が決定の対象である場合に限って書く

### B. 事実と根拠

- **B-1 MUST**: 事実は一次資料（実コード・公式ドキュメント・実測）と照合して書き、出典か確認方法を添える。
  確かめていないことは「未確認」と書く
- **B-2 SHOULD**: 判断の根拠になった実測と経緯は残す（反転テスト）。実測には日付と環境を添える。
  段階ごとの改善値や作業の経過はコミット本文に置く
- **B-3 MUST**: ADR 単体で読めるようにする。背景には一般論ではなく、このプロジェクトで実際に起きている問題と制約を書く。
  会話や口頭のやり取りにしか残っていない根拠に頼らない

### C. 決定と、決定しないこと

- **C-1 MUST**: 「決定」の節は、採る方式を 1 文で言い切ってから条項を並べる
- **C-2 SHOULD**: 不採用にした選択肢も、採らない理由とともに残す
- **C-3 SHOULD**: 「決定しないこと」の節を置き、項目ごとに引き継ぎ先を書く。
  引き継ぎ先は実在する文書（ADR・docs）か、判断のきっかけ（何が起きたら決めるか）にする。「将来の ADR で扱う」とだけ書かない

### D. 参照

- **D-1 SHOULD**: 作業の現場への参照（コミット SHA・PR・Issue）は「参照」節に集める。事実の出典は本文に添えてよい
- **D-2 MUST**: 行番号で参照しない。他の ADR は ID とリンクで指し、必要なら節の見出しを添える
  （例:「ADR-20260101-0003 の『決定』2」）

### E. 更新と整合

- **E-1 MUST**: 採用後に決定が変わったら、本文を書き換えずに新しい ADR を作る。
  新しい ADR の「関連」に置き換え元を書き、古い ADR のステータスを「置換」にして置き換え先を書く。
  一部だけ変わる場合は、古い ADR を「採用」のまま、ステータスの後ろに置き換え先を書く
- **E-2 SHOULD**: 採用後の追記はしない。前提だけが変わった（版の更新など）ならコミット本文に書き、決定が変わるなら E-1 に従う。
  読み手が誤解する事実の誤りに限り、日付付きの短い注記を足してよい
- **E-3 MUST**: ステータスは「提案」「採用」「却下」「置換」「廃止」のいずれかにする
- **E-4 MUST**: 索引（DECISIONS.md）の ID・タイトル・ステータス・決定日を ADR 本体と一致させ、各行から ADR へリンクする

### F. 表記

- **F-1 SHOULD**: 用語・ツール名はリポジトリ内の既存の表記にそろえ、初出の略語は定義する
- **F-2 SHOULD**: 「現在」「最新」「先週」のような時点に依存する表現を避け、日付と版で書く

### G. 採用前の点検

- **G-1 MUST**: 「採用」にする前に、決まっていないことを「決定」に混ぜていないかを確かめる。決まっていないことは「決定しないこと」へ移す
- **G-2 MUST**: 書き手とは別のコンテキストの点検役が、規約番号を根拠に指摘する。MUST の指摘を解消してからコミットする

## OK / NG 例

例はすべて作例。実在する ADR の文章は引用しない（決定が無効になった後に、例だけがノイズとして残るのを避けるため）。

### A-2: 進捗を書かない

NG:

```markdown
- [x] 検証環境に導入した
- [ ] 来週までに全端末へ反映する
```

OK:

```markdown
- 移行期間中は、旧形式と新形式のどちらの設定ファイルも読めること
```

### A-3: 実装の自由度を奪わない

NG:

```markdown
- `loadConfig()` で環境変数 `APP_STRICT=1` を読み、そのときだけ `cache.disable()` を呼ぶ
```

OK:

```markdown
- 厳格モードではキャッシュを使わない。モードの指定方法は実装に任せる
```

### B-2: 根拠は残し、作業の記録は外す

NG（作業の記録。反転テストで決定が変わらない）:

```markdown
| 段階 | 起動時間 |
|---|---|
| キャッシュ導入 | 320 → 290ms |
| 遅延読み込み | 290 → 210ms |
```

OK（判断の根拠。結果が逆なら採否が変わる）:

```markdown
- 常駐型は呼び出しごとに約 20ms 遅くなる（2026-01-10、手元の macOS で 30 回の中央値）ため採らない
```

### C-3: 引き継ぎ先を名指しする

NG:

```markdown
- 認証方式は将来の ADR で扱う
```

OK:

```markdown
- トークン失効時の扱いは決めない。利用者が 2 人を超えた時点で、別の ADR で決める
```

### E-2: 採用後の追記をしない

NG:

```markdown
## 追記（2026-02-01）: ツールを 2.0 に上げた

上の記述のうち、次の点が変わった……
```

OK: 版の更新はコミット本文に書く。決定が変わるなら新しい ADR を作り、古い ADR を「置換」にする。
